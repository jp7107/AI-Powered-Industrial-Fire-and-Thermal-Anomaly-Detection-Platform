# backend.md — ThermoWatch AI Backend Implementation Plan
**Project:** SIH 2026 · PS 26162 — AI-Based Detection and Classification of Industrial Fires and Persistent Thermal Sources (NASA FIRMS + OSM + Satellite)
**Scope of this file:** backend only — ingestion, database, GIS processing, classification, risk, alerts, simulation/NRT, APIs, jobs, security, deployment. No code. UI behaviour lives in `frontend.md`.

---

## 0. Problem alignment and honest limits

| PS deliverable | Backend answer |
|---|---|
| (i) Classify / segregate industrial fires from forest fires and other natural fires | Event-level **hybrid classifier** (fuzzy rules + gradient-boosted model) over 6 classes, with confidence, evidence and risk |
| (ii) GIS-based storage + map overlay visualisation | **PostgreSQL + PostGIS**, vector-tile endpoints (MVT), GeoJSON APIs, raster layers via tile server |

**Limits to state openly (in the report and UI):**
- FIRMS VIIRS pixels are ~375 m (MODIS ~1 km): a detection cannot show *what* is burning, only that a thermal anomaly exists there. Classification is **probabilistic decision support**, not ground truth.
- Distinguishing an accidental industrial fire from routine flaring depends on **history at that location** (baseline) and **facility context** (OSM), so the persistence registry is the most important component.
- OSM industrial coverage in India is incomplete; unmapped facilities will be classed by land cover and flagged "possible unmapped facility".
- Labelled ground truth is scarce → no large-scale supervised training; hence the rules-first hybrid (§9).

## 1. Data taxonomy — REAL / DEMO / SYNTHETIC / DERIVED

Every row carries `data_origin` and a `dataset_id`; APIs return them; the UI badges them.

| Category | Definition | Examples in this system | `data_origin` | UI badge |
|---|---|---|---|---|
| **REAL** | Unmodified observations from an external authoritative source | FIRMS detections (NRT or archive), OSM facilities, ESA WorldCover, WorldPop, Sentinel-2 chips, admin boundaries | `real_nrt`, `real_archive`, `real_static` | REAL |
| **DEMO** | A curated, **real historical** slice (or curated static bundle) used for offline showcase; timestamps are *never* shifted to look current | Downloaded FIRMS window (e.g., a stubble-burning fortnight), stored in `data/demo/` | `demo_curated` | DEMO |
| **SYNTHETIC** | Generated by us to exercise scenarios not reliably available in real data | Injected "refinery flare surge" detections around a real facility, synthetic events for load tests | `synthetic` | SYNTHETIC (hatched) |
| **DERIVED / AI** | Computed by our pipeline from the above | Events, clusters, class, probabilities, confidence, risk score/level, evidence, persistence registry, alerts, affected area, risk zones | `derived` (flag `is_derived=true`) | AI |

Rules: (1) real vs demo vs synthetic rows are separated by `dataset_id` and never mixed in one API response unless the dataset explicitly says so; (2) a derived object inherits the **weakest** origin of its inputs (synthetic > demo > real) → `events.data_origin`; (3) the UI cannot show "Live" unless `mode=live` **and** the dataset is `real_nrt`.

## 2. Architecture

```
            ┌────────────── Source adapters (ports) ─────────────┐
 FIRMS API ─┤ FirmsApiSource        (NRT/live)                    │
 Archive   ─┤ ArchiveFileSource     (historical/demo bootstrap)   │
 Replay    ─┤ ReplaySource          (simulation, virtual clock)   │
 Synthetic ─┤ SyntheticSource       (scenario injection)          │
            └───────────────────────┬─────────────────────────────┘
                                    ▼
   normalize → validate → dedupe/upsert → firms_detections (PostGIS)
                                    ▼
   process pipeline (SAME code in all modes):
   context enrich → cluster → event link/merge → persistence check →
   features → classify (rules+ML) → confidence → risk → evidence → alerts
                                    ▼
   FastAPI REST + MVT tiles + SSE  ◄── Redis (cache, pubsub, queue)
                                    ▼
                               React frontend
```
Key design principle: **one processing path, different source adapters.** Demo, Simulation and Live differ only in *where detections come from* and *what "now" means*.

**Stack:** Python 3.11 · FastAPI · SQLAlchemy 2 + GeoAlchemy2 + Alembic · PostgreSQL 16 + PostGIS 3.4 (+ `h3-pg` optional) · Redis · Celery (+ beat) · GeoPandas/Shapely/pyproj · rasterio · h3-py · scikit-learn + XGBoost + SHAP · httpx · tenacity · structlog · Prometheus client · TiTiler (raster tiles) · MinIO/S3 (imagery cache) · Docker Compose.

## 3. Data sources

### 3.1 NASA FIRMS (REAL)
- Products (India prototype): **VIIRS S-NPP NRT, NOAA-20 NRT, NOAA-21 NRT** (375 m, primary); MODIS NRT (1 km, optional/fallback). Archive/"Standard Processing" (SP) products for history.
- Access: FIRMS **Area API** (CSV) with a free `MAP_KEY` — request by bounding box (India ≈ `68,6,98,37.5`) and day-range; a country endpoint and a data-availability endpoint also exist. Respect the MAP_KEY quota (documented as a transaction budget per 10-minute window). *Verify parameters/limits against current FIRMS docs before coding.*
- Fields used: `latitude, longitude, bright_ti4 (or brightness), bright_ti5 (or bright_t31), scan, track, acq_date, acq_time (UTC), satellite, instrument, confidence (VIIRS: l/n/h; MODIS: 0–100), frp (MW), daynight, version`.
- SP archive files include a `type` attribute (e.g., presumed vegetation fire / active volcano / **other static land source** / offshore) that NRT feeds lack → used as **weak labels and validation for static/industrial sources** (confirm in current product docs).
- Latency: FIRMS distinguishes *ultra-real-time / real-time* (US & Canada only) from **NRT (globally, typically within ~3 h of observation)**; India is served by NRT. The system therefore documents itself as **near-real-time**.

### 3.2 OpenStreetMap industrial facilities (REAL)
- **Bulk:** Geofabrik India extract (`.osm.pbf`) filtered with osmium → GeoPackage/PostGIS (reliable for whole-country). **Incremental/targeted:** Overpass API by bounded tiles/states (`[timeout:180]`, `out geom`/`out center`), polite rate limits, cached responses, multiple mirrors.
- Tag → `facility_type` mapping (maintained in `config/facility_tags.yaml`; verify tag usage with taginfo before finalising):

| facility_type | Example OSM tags | hazard_weight (0–1) |
|---|---|---|
| refinery | `industrial=refinery`, `man_made=works`+`product=petroleum/oil` | 1.0 |
| petrochemical / chemical | `industrial=chemical`/`petrochemical`, `man_made=works`+`product=chemicals` | 0.95 |
| lng_gas_terminal / gas processing / oil-gas field | `industrial=gas`/`oil`, `man_made=petroleum_well`, `man_made=storage_tank`+`content=gas/oil`, `man_made=flare`/`man_made=chimney` (flare stacks) | 0.9 |
| power_plant (thermal) | `power=plant` + `plant:source=coal/gas/oil/lignite` | 0.8 |
| steel / metal | `industrial=steel_mill`/`metal`, `man_made=works`+`product=steel` | 0.75 |
| cement / kiln / brickyard | `industrial=cement`, `man_made=kiln`, `industrial=brickyard` | 0.5 |
| mining / quarry | `landuse=quarry`, `industrial=mine`, `resource=coal` | 0.5 (routes to Mining class) |
| landfill / waste | `landuse=landfill`, `amenity=waste_transfer_station` | 0.4 (often "Other") |
| other_industrial | `landuse=industrial`, `man_made=works` | 0.5 |

- Curated overrides (`data/curated/facility_overrides.csv`): fix names/operators/hazard tier, add missing flare-stack points, add known static sources; tagged `data_origin=real_static`, `source='curated'`.
- Store polygons and centroid; compute `area_m2`; reproject to a metric CRS (EPSG:7755 India NSF LCC) for distance/buffer logic. Display "© OpenStreetMap contributors (ODbL)" in the UI.

### 3.3 Land cover, population, boundaries, forest/farmland (REAL, static)
- **ESA WorldCover 10 m** (COG tiles, anonymous S3 read for India tiles): tree, shrub, grass, crop, built-up, bare, water, wetland etc. Built-up ≠ industrial → OSM needed.
- **Forest proximity:** WorldCover tree class + OSM `landuse=forest`, `natural=wood`, `boundary=protected_area`.
- **Farmland:** WorldCover cropland + OSM `landuse=farmland/orchard`.
- **Population:** WorldPop (100 m) or GHSL population grid → zonal sums for 1 km / 5 km.
- **Admin boundaries + gazetteer:** state/district polygons (Survey-of-India-consistent for display) and OSM `place=*`/GeoNames points → `place_name`, `state`, `district`.
- Context is **computed lazily and cached per H3 res-8 cell** (`cell_context`) the first time a detection appears there (whole-India precompute of 10 m rasters is unnecessary).

### 3.4 Satellite imagery / context
- **Sentinel-2 L2A via Copernicus Data Space Ecosystem** (STAC/OData search + Sentinel Hub Process API or TiTiler on COGs): 2.5 × 2.5 km chip around the event; **true colour (B4/B3/B2)** and **SWIR composite (B12/B11/B8A)** which highlights active burning/hot surfaces; cloud check with the scene-classification layer at the chip.
- Selection: latest scene within *N days* (default 10) with chip cloud < 30 %; else record `status='no_clear_scene'`. **Always store real `acquired_at`**; never present an old scene as "current".
- **NASA GIBS** WMTS for global daily context layers (public basemap/overlays).
- Optional stretch: **burn-scar (dNBR)** confirmation days after an event (helps wildfire/agri confirmation), Landsat thermal for large industrial complexes, VIIRS Nightfire (external, registration) as a validation reference for flares.
- Chips cached in object storage (`imagery_assets.storage_key`); requests queued asynchronously; failure never blocks event creation.

### 3.5 Weather (optional, phase 2)
Open-Meteo point weather (wind speed/direction, temperature) for risk context and the "Weather Overlay" layer. Off by default.

## 4. Data modes

### 4.1 Effective time
All time-relative logic uses `effective_now`:
| Mode | `effective_now` |
|---|---|
| Live | `now()` (UTC) |
| Demo | `dataset.period_end` (fixed) |
| Simulation | `sim_run.virtual_clock` |
`GET /status` returns it as `as_of`. "Last 7 days" = `[effective_now−7d, effective_now]`.

### 4.2 DEMO MODE
```
Local realistic dataset (real historical FIRMS slice + curated OSM/landcover + optional SYNTHETIC scenarios)
  → one-time loader → firms_detections (dataset_id='demo-v1')
  → processing pipeline run once in batch (chronological)
  → events / alerts / evidence stored
  → dashboard (static, no SSE updates)
```
- Labelled **"Demo dataset · <period>"**, never "Live". A pre-history window (≥ 90 days, ideally 365) is included or the global **baseline registry** (§7.4) is used so persistence works.
- Works offline (no FIRMS/Overpass/CDSE calls); Sentinel-2 chips for demo events are pre-cached.
- Synthetic scenarios are stored with `data_origin='synthetic'` and appear with the SYNTHETIC badge.

### 4.3 SIMULATION MODE
```
Historical/demo observations (real archive or demo dataset)
  → Replay engine (virtual clock, speed factor, simulated latency)
  → same ingest+processing pipeline
  → classification → risk → alerts
  → dashboard (SSE events at simulated pace)
```
- `sim_runs`: `id, source_dataset_id, start_ts, virtual_clock, speed (1×,60×,600×,3600×), latency_model (fixed/random 5–180 min), state (running/paused/stopped), seed`.
- Ticker (every 2 s real time) advances the clock by `speed×dt`; releases detections with `acq_datetime + simulated_latency ≤ virtual_clock`; writes them under `dataset_id='sim:<run_id>'` so live/demo data is untouched; emits SSE (`event.created/updated`, `alert.created`, `status.changed`) with `mode='simulation'`.
- Controls (admin): `start / pause / resume / speed / jump / reset` (reset deletes the sim scope). Deterministic given `seed`.
- UI label: "Simulation · virtual time …". Never "Live".

### 4.4 NRT / LIVE MODE
```
NASA FIRMS API (VIIRS NRT products)
  → scheduled ingestion (every 10 min)
  → normalize / dedupe → database
  → processing (cluster → features → classification)
  → risk → alerts
  → dashboard (SSE + polling)
```
- Overlapping fetch windows (last 24–48 h each run) absorb late-arriving records; dedupe guarantees idempotency.
- Freshness SLO: if `now − last_ingest_at > 3× interval` → status `stale` (amber) + system alert `data_stale`.

### 4.5 Real-time vs near-real-time
- **Real-time:** result available within seconds (or less) of the physical event and streamed continuously. Not what FIRMS provides.
- **Near-real-time (NRT):** result delivered after unavoidable acquisition, downlink, processing and publishing steps — for FIRMS outside the US/Canada typically **up to ~3 hours** after satellite observation — and each location is observed only at **overpass instants** (a few times per day across VIIRS satellites), not continuously.
- Implications: "detection frequency" and "persistence" are measured per overpass/day; an event may be hours old when first shown; dashboard timestamps show both **observation time** and **ingest time**; marketing copy must say "near-real-time".

### 4.6 Mode switching
`POST /admin/mode {mode, dataset_id|sim params}` updates `app_state`; API filters every query by the active `dataset_scope` (`live-india`, `demo-v1`, `sim:<id>`); SSE emits `status.changed`. Jobs for live ingestion are disabled unless mode = live (or run in the background with separate scope, optional).

## 5. Ingestion, normalisation, deduplication

### 5.1 FIRMS ingestion job (`firms_poll`)
1. For each product (`VIIRS_SNPP_NRT`, `VIIRS_NOAA20_NRT`, `VIIRS_NOAA21_NRT`) call Area API for India bbox, `day_range=2` (overlap).
2. Parse CSV → dataframe; validate schema (missing/renamed columns → alert `schema_drift`, abort product only).
3. **Normalise** to canonical columns (below); clip to India polygon (`ST_Intersects`).
4. Upsert with `ON CONFLICT DO NOTHING` on `dedupe_key`; count `rows_new/rows_dup`.
5. Record `ingest_runs`; publish `ingest.completed` (Redis) → triggers `process_new_detections`.

### 5.2 Canonical normalisation
| Canonical field | VIIRS source | MODIS source | Notes |
|---|---|---|---|
| `acq_datetime` (UTC timestamptz) | `acq_date` + `acq_time` (HHMM UTC) | same | Stored UTC; IST at API/UI |
| `brightness_primary_k` | `bright_ti4` | `brightness` | Brightness temperature, not flame temperature; VIIRS I-4 saturates ~367 K |
| `brightness_secondary_k` | `bright_ti5` | `bright_t31` | |
| `frp_mw` | `frp` | `frp` | MW per pixel |
| `confidence_raw` | `l/n/h` | 0–100 | |
| `confidence_norm` (0–1) | l=0.25, n=0.60, h=0.90 | value/100 | Mapping configurable |
| `pixel_area_km2` | `scan×track` | `scan×track` | Off-nadir pixels larger |
| `sensor`, `satellite`, `product` | | | e.g., `VIIRS`, `N20`, `VIIRS_NOAA20_NRT` |
| `daynight` | `D/N` | `D/N` | |
| `geom` | Point(lon, lat) EPSG:4326 | | |
| `dedupe_key` | `sha1(product|satellite|round(lat,5)|round(lon,5)|acq_datetime)` | | |
| `data_origin`, `dataset_id`, `ingest_run_id` | | | |

Validation: lat/lon inside India bbox; `frp ≥ 0`; brightness 250–420 K; timestamp not in the future (> 10 min) → violations go to `rejected_records` (reason) instead of failing the run.

### 5.3 Deduplication layers
1. **Row level:** unique `dedupe_key`, idempotent re-ingest, overlapping windows.
2. **NRT ↔ SP reconciliation:** when SP data for the same period appears (weeks–months later), upsert over NRT rows (match on satellite + coordinates + time), mark `product` and bump `version`; recompute affected events.
3. **Cross-sensor:** detections from different satellites are separate observations (kept) but linked to the same event by clustering.
4. **Event level:** overlapping/adjacent clusters are merged (union of events, `merged_into` pointer on the loser).
5. **Alert level:** `dedupe_key` + cooldown (§12).

### 5.4 Historical FIRMS backfill (one-off, `backfill_archive`)
Download 1–3 years of India SP data (annual/monthly CSVs) → same normaliser → `firms_detections` (`dataset_id='archive-india'`, `data_origin='real_archive'`, partitioned by month). Used for: persistence/baseline registry, model features, weak labels (`type`), demo/simulation sources, evaluation.

## 6. Database

### 6.1 PostgreSQL + PostGIS vs MongoDB
| Criterion | PostgreSQL + PostGIS | MongoDB (2dsphere) |
|---|---|---|
| Spatial functions | Full: `ST_DWithin`, `ST_ClusterDBSCAN`, `ST_Union`, KNN `<->`, `ST_AsMVT`, raster/H3 ecosystem | Limited: near/within/intersects; no clustering, no MVT |
| Spatial + relational joins (detection→event→facility→alert) | Native, transactional | Manual/aggregation pipelines |
| Time-series & aggregation | SQL, partitioning, materialised views | Aggregation framework OK |
| Dedupe/idempotency | Unique constraints, `ON CONFLICT` | Unique index possible |
| Tile serving | Direct MVT from SQL | Needs external service |
| Ecosystem (QGIS, GeoServer, GeoPandas) | Excellent | Weak |
**Decision: PostgreSQL + PostGIS.** Semi-structured evidence/probabilities live in `JSONB` columns. Redis is auxiliary (cache, pub/sub, queue) — not a system of record.

### 6.3 Spatial query patterns (specifications, not final code)
- **Nearest facility:** KNN (`<->`) on `facilities.centroid`, refined with `ST_Distance` in EPSG:7755; `ST_DWithin` for the ≤ 1–5 km candidates; polygon containment (`ST_Contains`) for `in_facility`.
- **Event clustering:** `ST_ClusterDBSCAN` on projected geometries over the recent detection window (§7.2).
- **Viewport queries:** `geom && ST_MakeEnvelope(bbox)` + filters; MVT via `ST_AsMVTGeom` + `ST_AsMVT`.
- **Buffers/rings:** `ST_Buffer(geom::geography, r)` or projected buffers for 500 m / 1 km / 5 km.
- **Zonal context:** raster window read (rasterio) around the event centroid → fractions/sums → cached in `cell_context`.
- **Region rollups:** `ST_Intersects` with `admin_boundaries` (or precomputed `state/district` on the event).
- Use projected CRS (**EPSG:7755**) for metric operations; keep 4326 for storage/tiles.

## 7. Geospatial processing

### 7.1 Industrial proximity analysis
Per event: nearest facility (name, type, hazard_weight), distance from footprint edge to facility polygon (0 if inside), counts of facilities within 1/2/5 km, whether the event lies in a `landuse=industrial` polygon, facility type mix within 2 km. Facility distance uses the *nearest of* polygon or flare-stack points.

### 7.2 Spatial(-temporal) clustering and event lifecycle
1. **Candidate set:** detections from the last 72 h (open window) + new detections.
2. **Cluster:** DBSCAN in EPSG:7755, `eps ≈ 750 m` (~2 VIIRS pixels), `min_points = 1` (single-pixel events allowed); time-chained with a **48 h gap** rule (ST-DBSCAN behaviour).
3. **Link:** cluster → existing open event if footprint (buffered 1 km) intersects; several intersected events → **merge** (keep oldest id, set `merged_into` on others); none → **new event** (`status=active`).
4. **Persistent-source handling:** clusters falling in cells of a registered `thermal_source` update that source's single long-lived **persistent event** (`event_kind='persistent'`) — so "Persistent Sources" counts distinct sources, not daily noise. A statistically anomalous pulse at a source spawns a separate **transient event** (`parent thermal_source_id`) that can become *Industrial Fire*.
5. **Lifecycle:** `active` (detection in last 24 h) → `monitoring` (24–48 h) → `closed` (> 48 h; persistent events never close while source active). Sweep every 15 min.
6. **Derived geometry:** footprint = union of 375 m pixel squares (from `scan/track`) or concave hull buffered by half pixel; `affected_area_km2 = footprint area` (estimate, labelled as such).
7. **Persistence for events:** `persistence_days` = distinct IST dates with detections in the footprint; `detection_count` = detections (pixel observations).

### 7.3 Detection frequency
Per event/cell: detections per day, per overpass count, day/night split, active days ÷ observed days over 30/90/365 windows. Frequency is normalised by number of possible overpasses when known (cloud cover unknown → treated as noise; documented).

### 7.4 Persistence detection & baseline registry (`persistence_registry_rebuild`, nightly + one-off from archive)
1. Assign each archived detection to an **H3 res-8** cell (edge ≈ 460 m; pixel jitter tolerated by counting k-ring 1).
2. Per cell over 30/90/365 days: `days_detected`, `months_detected`, `night_ratio`, `median_frp`, `p90_frp`, `frp_cv`, sensors.
3. **Persistent** if (`days_detected_90 ≥ 12` **or** `persistence_ratio_90 ≥ 0.25`) **and** `months_detected_365 ≥ 3` **including months outside the local crop-residue burning seasons** (guards against fields that burn every Oct–Nov) **or** night detections regularly present; SP `static_type = other static land source` boosts confidence.
3b. Thresholds live in `config/persistence.yaml` and are tuned on known cases (e.g., refineries/flares, steel plants, coal-mine-fire areas).
4. Merge adjacent persistent cells into `thermal_sources`; link to `facility_id` if ≤ 1 km; store baseline stats (`median_frp`, `p90_frp`, `frp_cv`).
5. The registry is **baseline data independent of dataset scope**, so Demo/Simulation/Live all classify against the same history.
6. Anomaly test at a source: `frp_ratio = event_peak_frp / p90_frp` and z-score of FRP vs history; new footprint growth beyond baseline footprint; sudden appearance of many pixels.

## 8. Feature engineering (per event; `feature_set_version` tracked)

| Group | Features | Source |
|---|---|---|
| Intensity | `peak_frp_mw, mean_frp_mw, sum_frp_mw, max_brightness_k, brightness_ti4_minus_ti5, frp_per_pixel` | FIRMS |
| Detection quality | `best_confidence_norm, low_conf_fraction, sensors_count, day_night_mix, off_nadir_flag` | FIRMS |
| Cluster shape | `pixel_count, area_km2, compactness (area/hull), elongation, growth_rate_km2_per_h, spread_direction_consistency` | derived |

Rule for all features: **null-safe** (missing → NaN + `data_completeness` score), computed in `features/` module with unit tests; identical code path for training and inference.

## 9. Classification

### 9.1 Target classes
`industrial_fire · gas_flare_persistent · wildfire_forest · agricultural_burning · mining_activity · other_thermal`

### 9.2 Comparison
| Criterion | Rule-based | Random Forest | XGBoost | **Hybrid (rules + ML)** |
|---|---|---|---|---|
| Training data needed | None | Labelled events (hundreds+) | Labelled events (hundreds+) | Little: rules bootstrap, small verified set refines |
| Explainability | Highest (named rules) | Medium (importances) | Medium–high (SHAP) | Highest (rule trace + SHAP) |
| Cold-start / new region | Works day 1 | Weak without labels | Weak without labels | Works day 1, improves with feedback |
| Handles feature interactions | Manual | Yes | Yes (best on tabular) | Yes |
| Robustness to missing features | Good (fuzzy membership) | Needs imputation | Native NaN handling | Good |
| Calibrated probabilities | Via normalisation | Needs calibration | Needs calibration | Calibrated blend |
| Failure mode | Brittle thresholds | Overfits label bias | Overfits tiny data | Disagreement flagged → review |
| Effort | Low | Medium | Medium | Medium |
| Fit for this prototype | Good baseline | Comparison baseline | Good if labels exist | **Recommended** |

### 9.3 Recommended approach: Hybrid (no large-scale training)
1. **Rule engine (ships first):** fuzzy rules produce a *support score per class* (0–1) with named evidence. Deterministic, tunable in `config/rules.yaml`.
2. **ML refiner (v2):** XGBoost (RandomForest kept as benchmark) on the §8 features, trained on a **small, weakly-labelled set**:
   - weak labels from *high-confidence rules* (support > 0.8, margin > 0.4),
   - archive `static_type` (static land source → persistent),
   - known-facility registry / curated known cases,
   - user feedback (`labels`).
   **Evaluation only on an independent, hand-verified set** (a few hundred events checked with Sentinel-2 SWIR, news/known incidents), split **spatially** (by state/grid) to avoid leakage. Otherwise the model merely re-learns the rules and accuracy claims would be circular.
3. **Blend:** `p_final = w_r·p_rules + w_m·p_ml` (start `w_r=0.6, w_m=0.4` when a model exists; rules-only otherwise). Disagreement (top classes differ) → `needs_review=true`, confidence penalised. Safety override: hard rules (e.g., inside refinery polygon + FRP anomaly) can set a floor on `industrial_fire` for alerting.
4. **Calibration:** isotonic/Platt on the validation set; probabilities reported as calibrated when available.
5. Model artefacts versioned in `model_registry`; `model_version` and `rules_version` stored on every event; shadow mode allows running the ML model without affecting output.

### 9.4 Rule cascade (thresholds illustrative, configurable)
| Rule | Fires when (fuzzy memberships) | Class support |
|---|---|---|
| R0 Quality gate | single detection, FIRMS confidence low, no facility ≤ 2 km, low FRP | → `other_thermal` (`low_quality`) |
| R1 Persistent source | `thermal_source` match **or** `days_detected_90` high & `months_detected_365 ≥ 3`; FRP within baseline (`frp_ratio ≤ ~2`); night detections present; within/≤ 1 km of industrial facility (boosts) | `gas_flare_persistent` (sub-type: flare/furnace/kiln/power) |
| R2 Industrial fire | ≤ 1 km or inside industrial/hazard facility **and** (`frp_ratio ≥ ~3` or z-score high or new source) **and** built-up/bare surroundings; footprint growth or multi-pixel cluster | `industrial_fire` |
| R3 Mining | inside quarry/mine polygon or bare/sparse land + mining tags; moderate persistence; coal-fire pattern (long-lived low-FRP) | `mining_activity` |
| R4 Wildfire | forest/tree-shrub fraction ≥ ~0.5 or in forest/protected polygon; facility > 5 km; short-lived; spreading footprint; forest-fire season | `wildfire_forest` |
| R5 Agricultural burning | cropland fraction ≥ ~0.5; no facility ≤ 2 km; duration ≤ ~3 days; small FRP; afternoon-overpass dominance; crop-residue season; many neighbouring small events | `agricultural_burning` |
| R6 Fallback | none dominant, or conflicting evidence (urban waste burning, brick kilns, landfills) | `other_thermal` |
Supports are normalised (softmax with temperature) to `class_probs`; `event_class = argmax` if `p_top ≥ 0.45`, else `other_thermal` + `needs_review`.

### 9.5 Confidence calculation (classification confidence, **separate** from FIRMS confidence)
```
class_confidence = p_top × (0.60 + 0.20·agreement + 0.10·detection_quality + 0.10·data_completeness)
```
- `p_top`: calibrated top-class probability.
- `agreement`: 1 if rules and ML agree (or rules-only), 0.5 if margin small, 0 if they disagree.
- `detection_quality`: `best_confidence_norm` of FIRMS detections (× sensor factor).
- `data_completeness`: share of features available (OSM coverage, land cover, history depth).
Displayed as %, plus `detection_confidence` (FIRMS) shown separately. Weights are config, validated by calibration plots.

## 10. Risk scoring (0–100)
```
risk = 100 × clip( 0.20·intensity + 0.20·anomaly + 0.20·asset_criticality
                 + 0.15·population_exposure + 0.10·escalation + 0.15·class_severity_conf )
```
| Component | Definition (0–1) |
|---|---|
| `intensity` | FRP percentile within its class over last 365 d (or vs. class-specific reference) |
| `anomaly` | `min(1, log(frp_ratio_vs_p90)/log(5))` for facility/source events; 0 for non-facility |
| `asset_criticality` | facility `hazard_weight` × proximity decay (1 inside polygon → 0 at 2 km) |
| `population_exposure` | `min(1, log10(1+pop_5km)/log10(1+P_ref))` (P_ref e.g., 100 000) |
| `escalation` | footprint growth rate, increasing FRP trend, duration/persistence beyond normal, multiple sensors confirming |
| `class_severity_conf` | class prior (industrial 1.0, wildfire 0.7, mining 0.4, flare 0.35, agri 0.3, other 0.15) × `class_confidence` |
Levels: **Critical ≥ 80 · High 60–79 · Medium 35–59 · Low < 35** (configurable). Routine flaring inside baseline scores low even next to a refinery (anomaly term ≈ 0). `risk_components` stored for the UI breakdown. Optional weather term (wind toward populated area) in phase 2.

## 11. Explainability / evidence
- Each event stores 6–10 ordered `event_evidence` items: `label`, plain-language `text` (template-based, e.g., "Detected 320 m from *<facility>* (OSM)", "Detected on 6 distinct days (18 detections)", "FRP 3.4× the facility's 90-day baseline", "78 % built-up/bare land within 1 km"), signed `contribution` toward the winning class vs. runner-up, `source_tag` (FIRMS/OSM/WorldCover/derived), `origin`.
- **Rule trace:** which rules fired and their support. **ML part:** SHAP (TreeExplainer) top ±k features, mapped back to readable labels.
- Text is **template-generated** (no free-form LLM claims); any future LLM summary must be marked AI and grounded in these fields.
- Additional context artefacts: land-cover breakdown, facility card, baseline comparison, similar past events, imagery assets, data-quality flags (`osm_sparse_area`, `no_clear_imagery`, `low_history`).

## 17. Error handling, logging, security

### 17.1 Error handling
- Outbound calls: `httpx` timeouts (connect 5 s, read 60 s), `tenacity` retries (exponential backoff + jitter), **circuit breaker** per provider (FIRMS, Overpass, CDSE); provider allow-list (SSRF protection).
- Partial-failure isolation: a failing product/tile/facility batch does not abort others; failed units go to `failed_jobs` (dead-letter) with replay.
- Degradation: no imagery → event without chips (`pending`); Overpass down → use cached facilities; FIRMS outage → status `stale`; ML model unavailable → rules-only (`model_version=null`).
- API: RFC-7807 errors with stable `code`, `request_id`; input validation via Pydantic; DB constraint violations mapped to 409/422.
- Data quality: schema-drift detector, row-count anomaly detector, invalid-record quarantine.

### 17.2 Logging & observability
- `structlog` JSON logs with `request_id, job_id, run_id, dataset_id, mode, source, event_id`; log levels per module; no secrets/PII.
- Prometheus metrics: ingest rows/latency, freshness seconds, pipeline duration, events created/updated, classification distribution, alert counts, API latency/error rate, tile cache hit rate, queue depth. Grafana dashboard; optional Loki for logs; alerts on freshness/error spikes.
- Audit log for admin actions (mode switches, rule edits, acknowledgements, label changes).

### 17.3 Security
- AuthN: OAuth2/JWT (short-lived access + refresh in httpOnly cookies); roles `viewer / analyst / admin`; public read-only demo can be enabled with rate limits, admin endpoints always protected.
- Transport & headers: HTTPS/HSTS, CSP, CORS allow-list, secure cookies.
- Rate limiting (Redis), request size limits, pagination caps (`limit ≤ 500`), tile zoom limits.
- Secrets (FIRMS `MAP_KEY`, CDSE credentials, DB, JWT keys) in env/Docker secrets — **never** exposed to the frontend or committed.
- DB: least-privilege roles (`api_ro`, `pipeline_rw`, `admin`), parameterised queries only, network-isolated DB/Redis.
- Supply chain: pinned dependencies, `pip-audit`, Dependabot, container scanning.
- Data sensitivity: facilities are public OSM data; do not add non-public infrastructure data; emphasise "decision support, verify before action" in alert text.
- Licences: ODbL (OSM), CC-BY 4.0 (WorldCover), NASA/Copernicus open-data terms; attribution surfaced via `/layers` and the "About data" page.

## 21. Testing, delivery phases, risks

**Testing:** golden-file pipeline tests (fixed detections → expected class/risk), unit tests for each feature and rule, spatial correctness tests on small fixtures, idempotency tests (double ingest), simulation determinism test, API contract tests vs OpenAPI (shared with frontend MSW), load test on tile and `/events/map`, failure-injection (FIRMS 500, Overpass timeout, CDSE 429).

**Evaluation (for the SIH report):** per-class precision/recall/F1 and confusion matrix on the hand-verified set; recall of persistent sources against a reference list (e.g., known flares/plants); alert precision (false-alarm rate per week); rules vs RF vs XGBoost vs hybrid comparison on the same held-out set.

**Phases (2–3 devs):**
| Phase | Deliverable |
|---|---|
| B0 (2 d) | Repo, Compose, PostGIS schema, migrations, config, `/status`, `/layers`, OpenAPI skeleton (shared with frontend) |
| B1 (3 d) | FIRMS adapter + normaliser + dedupe; archive backfill; OSM bulk load; admin boundaries/gazetteer |
| B2 (3 d) | Clustering, event lifecycle, proximity, context cache (land cover, population) |
| B3 (3 d) | Persistence registry + baseline anomaly; feature engineering |
| B4 (3 d) | Rule engine, confidence, risk, evidence; alerts; KPIs/analytics/tile/event APIs |
| B5 (3 d) | Demo dataset + synthetic scenarios; simulation engine; SSE |
| B6 (3 d) | Imagery service; ML refiner + evaluation harness; hardening (security, logging, metrics), deployment |

**Top risks & mitigations:** sparse labels (→ rules-first, spatial CV, feedback loop); OSM gaps (→ curated overrides, land-cover fallback, "possible unmapped facility" flag); FIRMS/API quota or outage (→ overlap windows, caching, stale status, demo/sim fallback); seasonal agricultural repeats mistaken for persistent sources (→ month-diversity/night criteria); imagery unavailability (→ async, honest `no_clear_scene`); over-claiming (→ "near-real-time", "decision support", provenance badges everywhere).
